# etcd revision 爆炸：高频续约撑爆 8GB 存储导致服务发现全挂

## 先搞懂 etcd 和相关概念（通俗版）

### etcd 是什么

etcd 是**分布式 KV 存储**，可以理解成一个**高可用的配置中心 + 服务注册中心**。Kubernetes 就是用 etcd 存所有集群状态。

类比成**公司前台的花名册**：
- 每个服务（员工）到前台登记自己的名字和位置：`我在这里，可以找我`
- 其他服务想知道谁在哪，查一下花名册就行
- etcd 保证这本花名册任何时候都是**一致的、可靠的**

### Lease（租约/续约）

Lease 是 etcd 的**临时登记机制**：
- 服务节点登记时说："我叫节点A，但我不保证一直在这里"
- 登记时带一个**有效期**（如 5 秒）
- 节点必须**每 1 秒**刷新一次："我还活着！"
- 如果到期没刷新，etcd 认为这个节点死了，自动删除登记

就像前台登记时说："我工位在 3 楼，但可能随时换座位，5 分钟内没来更新说明我换位置了。"

### Revision（版本号）

etcd 每次数据变化都会生成一个**全局递增的版本号**（revision）。这不是单纯覆盖旧值，而是**保留历史版本**——类似 Git 每次提交都生成一个新 commit，而不是直接覆盖上一个 commit。

```
初始状态:                    revision = 1
节点A注册:  key=/nodes/A    revision = 2  ← 写了一条新记录
节点A续约:  key=/nodes/A    revision = 3  ← 又写了一条
节点A续约:  key=/nodes/A    revision = 4  ← 又写了一条
…… 一小时后 ……              revision = 3600
…… 一天后 ……                revision = 86400
```

**关键：** 虽然 key 没变、值没变，但每次续约都在**追加新版本**，旧版本数据占着磁盘空间不释放。

### Auto-compaction（自动压缩）

压缩就是**清理历史 revision**，只保留最近 N 分钟/小时的版本。相当于 Git 的 `git gc` 或数据库的 VACUUM。

**问题：** 不压缩 = 历史版本永远不删 = 磁盘只进不出 = 早晚撑爆。

## 场景

外呼服务依赖 etcd 做服务发现：拨打节点每 1 秒向 etcd 续约注册（lease TTL=5s），外呼服务收到请求后从 etcd 拉取可用节点列表选择一个进行拨打。

某天下午，所有外呼突然失败。

## 根因链

```
正常运行时：
  拨打节点每 1s 续约一次 → etcd 每次续约产生一条新 revision
  → etcd 没开自动压缩 → 历史 revision 只增不减
  → 几个月积累到 4000 万+ 条 revision → 8GB 存储打满
  → etcd 不可写（空间耗尽）

故障发生时：
  etcd 不可写 → 所有节点 lease 无法续约 → 5 秒后全部过期
  → 可用节点列表变空 → 所有外呼请求找不到拨打节点 → 全部失败
  → 影响 602 个坐席，持续 24 分钟
```

## 为什么恢复那么难（关键教训）

事故报告里的恢复过程非常典型，暴露了 etcd 的一个致命特性：

```
14:12 重启 etcd 节点          → 空间没释放，集群仍 unhealthy
14:13 执行数据压缩            → 集群已 unhealthy，压缩命令报错
14:15 调整存储 8G → 16G      → 节点能启动但 unavailable，仍 unhealthy
14:18 用备份数据单节点启动    → 仍然失败，怀疑数据已损坏
14:29 放弃恢复，切回老系统    → 恢复成功
```

**etcd 的恢复死胡同：**

| 尝试 | 为什么失败 |
|------|-----------|
| 重启 | etcd 重启不会自动清理 revision，空间依然满 |
| 执行压缩 | 集群 unhealthy 时，压缩 API 拒绝执行 |
| 扩容磁盘 | 扩容后 etcd 可以启动，但数据量太大导致 unavailable |
| 备份恢复 | 备份没验证过可恢复性，到用时发现不行 |

**核心矛盾：** 存储满了 → 集群 unhealthy → 无法执行任何管理操作（包括压缩）→ 无法恢复 → 死锁。唯一的恢复路径是在**集群还健康时**就做好压缩策略。

## 为什么扩容救不了（关键细节）

事故报告里写：扩容 8G → 16G，重启节点后 still unavailable。很多人会疑惑——空间够用了为什么还不行？

这里有一个对 etcd 分布式共识机制的误解。

### 存储满的时候，etcd 内部已经乱了

etcd 不是 MySQL，磁盘满了抛个错就行。它是**分布式共识系统（Raft）**：

```
正常时：
  每秒续约 → 写入成功 → 所有节点承认这个版本
  三个节点数据始终保持一致

空间打满时：
  部分写入成功、部分失败（网络抖动 + 磁盘满的边界状态）
  → 各节点看到的 revision 不一致
  → 有的节点有 key A，有的没有
  → Raft 多数派被破坏
  → 选不出 leader → 集群进入 unhealthy 状态
```

**关键：** 在空间满退出 healthy 状态之前，数据一致性已经被破坏了。这时候问题不是"空间不够"，而是"三个节点的数据对不上了"。

### 扩容解决了空间，但没解决数据对齐

```
扩容 8G → 16G
重启节点 N1
  → etcd 进程起来了
  → N1 尝试联系 leader 同步数据
  → 但集群没有 leader（选不出来）
  → N1 尝试自己当 leader
  → 但 N1 的数据版本和 N2、N3 不匹配
  → Raft 拒绝：不能用一个对不上的数据当 leader
  → 显示 "unavailable"（进程活着，但不在集群里工作）
```

类比：
> 三个记账员各有一本账本。
> 笔满了写不进去，三本账本已经对不上了。
> 换了本更大的账本（扩容），但三本账本的数据还是对不上。
> 重开也没用——谁的数据才是对的？

### 备份数据为什么也恢复失败

事故报告里写的"尝试使用备份数据单节点启动，仍旧失败"，这是第二个隐含假设被击穿的案例。

#### 备份是什么

etcd 的备份不是"再搭一套集群"，而是在正常节点上执行一条命令导出的文件：

```bash
etcdctl snapshot save /backup/etcd-20241128-snapshot.db
```

导出一个 `snapshot.db` 文件，里面是**那一刻 etcd 全量数据的快照**，类似 MySQL 的 `mysqldump`。

"用备份单节点启动"就是拿这个文件恢复成一个新 etcd 进程，跟原来的三节点集群没有任何关系：

```
崩溃的集群：
  etcd N1 ←→ etcd N2 ←→ etcd N3（三节点 Raft，全 unhealthy）

单节点恢复：
  备份文件 snapshot.db
  → 恢复成数据目录
  → 启动一个新 etcd（单节点，不跟 N1/N2/N3 通信）
  → 里面有备份那一刻的数据
  → 但跟原集群没有关系
```

#### 为什么失败了

可能的原因（按概率排序）：

| 原因 | 说明 | 类比 |
|------|------|------|
| **备份太旧** | 备份可能是几天甚至几周前的，恢复出来的节点列表为空或过时，服务用不了 | U 盘里存的是上个月的员工名册，这个月一半人调岗了 |
| **备份从未验证过可恢复** | `snapshot save` 命令返回了成功，但没人试过能不能 restore。文件可能损坏或不完整 | 装了监控摄像头但从来没回放过录像 |
| **版本兼容性** | 备份在旧版本 etcd 导出，恢复在新版本 etcd，格式不兼容 | Word 2003 文档在 Word 2024 打开乱码 |

#### 核心教训："做了备份" ≠ "备份能恢复"

这是一个极其常见但很少被验证的隐含假设：

```
备份流程：
  crontab 每天凌晨执行 snapshot save
  → 文件写入 /backup/ 目录
  → 磁盘空间监控显示文件存在，大小正常
  → 所有人都觉得"我们有备份了"

但实际上没验证过：
  这个文件真的能用 etcdctl restore 恢复吗？
  恢复出来的数据是不是完整的？
  恢复后服务能不能正常启动？
```

**正确的做法是定期做恢复演练** — 不只是"备份成功"的告警，而是**每个月选一台测试机器，跑一遍完整的 restore + 启动 + 数据校验流程**。如果 restore 脚本在演练中被发现有问题，那它就不是"浪费时间的测试"，而是救了一次命。

这也是为什么事故修复里最终方案是"切回科天"（老系统）而不是靠备份恢复——因为备份这条逃生通道本身就靠不住。

**最根本的预防：**
- ✅ `--auto-compaction-retention=1h`（只说这一句，等出事再压缩就晚了）
- ✅ 磁盘使用率告警（> 75% 就要处理，别等到 95%）
- ✅ 定期验证备份可恢复

### 1. etcd 的 revision 是一个隐形的磁盘消耗者

很多人把 etcd 当成"配置存进去就不变了"，但 lease 续约这种看似无害的操作，每次都是一次**写入**，每次写入都产生一个**永久的 revision**。

一个简单的计算：
- 10 个节点，每秒续约一次
- 一天：10 × 86400 = 86.4 万条 revision
- 一个月：约 2600 万条 revision
- 如果每条 revision 大约 200 字节 → 一个月就超过 5GB

**解决方式极其简单：开启自动压缩。** etcd 配置里加一行 `--auto-compaction-retention=1h`，只保留最近 1 小时的 revision，旧的全清理掉。

但就是这种一行配置的事，没有它，几千万条 revision 就来了。

### 2. 高频续约的设计需要审视

1 秒续约 5 秒过期，这个设计本身值不值得？

| 方案 | 写入频率 | etcd 压力 | 发现节点挂掉的时间 |
|------|---------|-----------|------------------|
| 1s 续约 / 5s TTL | 1 次/秒/节点 | 高 | 最多 5 秒 |
| 10s 续约 / 30s TTL | 0.1 次/秒/节点 | 低 | 最多 30 秒 |
| 30s 续约 / 90s TTL | 0.03 次/秒/节点 | 很低 | 最多 90 秒 |
| 被动探测 + 长 TTL | 极少写入 | 几乎无压力 | 取决于探测间隔 |

对于一个外呼系统来说，30 秒才知道节点挂了 vs 5 秒才知道，区别真的那么大吗？但 30 倍的压力差对 etcd 存储的影响是实打实的。

### 3. "兼容 etcd 不可用" ≠ "兼容 etcd 所有故障模式"

事故报告里有一句话很典型：

> "外呼服务正常能兼容 etcd 不可用的场景，但遗漏了 etcd 可用但无可用拨打节点的场景"

这是一个**边界条件遗漏的经典模式**：

| etcd 状态 | 服务有没有处理 |
|-----------|-------------|
| etcd 正常，有节点 | ✅ 正常 |
| etcd 挂了 | ✅ 有降级处理 |
| **etcd 正常，但没节点** | ❌ **没想到这个情况** |

在分布式系统里，"组件处于中间态"（活着但返回空/慢/部分数据）比"组件彻底挂了"更难处理，也更容易被遗漏。

一个合理的兜底：**保留最近一次从 etcd 读到的可用节点列表作为本地缓存**；etcd 返回空时，用缓存里的旧列表继续服务，同时告警。宁可打到一台可能已经不在了的节点（失败重试），也不要让所有请求直接失败。

### 4. 写满 vs 读满：两种故障，两种性格

| | 存储写满 | CPU/内存打满 |
|--|---------|-------------|
| 表现 | 优雅地拒绝写入，只读不受影响 | 随机超时，乱七糟八的错误 |
| 恢复难度 | 难（如上所述，可能死锁） | 简单（停掉部分请求就恢复） |
| 预防 | 容量监控 + auto-compaction | 限流 + 自动扩缩容 |

etcd 存储写满是**最疼的一种故障模式**：不会立刻崩，但一旦进入 unhealthy，连自救都做不了。

## 一句话总结

> etcd 的 lease 续约看似轻量，但每次续约都是一次写入，每次写入都有一个永久的 revision。不压缩、不监控，revision 就是埋给你的定时炸弹。**等炸了再想拆，已经来不及了。**
