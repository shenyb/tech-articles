# P2P镜像分发系统中 peer 节点缓存续约失效引发的连锁雪崩

## 场景

Kubernetes 集群中，某物理交换机故障导致 100+ 台节点断网，触发数千个容器迁移。迁移后新节点需要拉取镜像，由 P2P 镜像分发系统（如 Dragonfly/Dragonfly2）的 peer 节点提供缓存加速。

## 问题

迁移大量发生时，大量容器处于 Pending 状态，无法启动。

## 根因链

```
交换机故障 → 节点断网 → 容器被驱逐迁移
  → 新节点上大量并发镜像拉取请求
  → 本应被 peer 节点缓存命中，但 peer 缓存被清理了
  → 所有请求回源到镜像仓库
  → 仓库网络带宽打满 → 响应变慢 → 容器超时无法启动
```

### 关键失效点：Peer 节点续约（lease renewal）失效

P2P 分发系统的工作原理：
- 每个 peer 节点缓存已拉取的镜像层，并向其他节点提供下载
- peer 通过**续约机制**（lease/keepalive）向调度中心报告自己还活着，上面的缓存有效
- 调度中心根据存活 peer 列表分发下载请求

失效原因（两个叠在一起）：

1. **containerd 环境兼容性问题** — 续约逻辑在 Docker 环境下正常运行，但在 containerd 环境下获取存活容器列表失败（API 差异），导致 peer 认为自己管理的容器都已不存在
2. **镜像仓库鉴权问题** — 续约时向仓库验证缓存有效性的请求因鉴权失败被拒绝

这两种原因共同导致 peer 节点上的缓存被认为是无效的，被清理掉。

## 类比

想象一个社区图书馆网络：
- 每个小区（peer）有自己的分馆，缓存热门书籍
- 分馆定期向总馆报告"我还开着，书还在"
- 突然一个小区整栋楼停电（交换机故障），居民（容器）被临时安置到其他小区
- 但安置到新小区后发现，新小区的分馆因为没有及时续约，把所有书都还回总馆了
- 于是所有居民都涌向总馆借书 → 总馆排长队 → 大家借不到书

## 解决方案

1. **修复 peer 续约 bug** — 解决 containerd 兼容性和鉴权问题
2. **镜像仓库扩容** — 提高 origin 的带宽容量，为回源场景留余量
3. **增加仓库带宽告警** — 让回源流量膨胀时能被及时发现
4. **故障演练** — 定期对核心依赖链路做混沌工程测试

## 启示

### 1. 问题一直在潜伏，故障只是「显影液」

这个 bug（续约失败导致缓存被清空）在交换机故障之前就已经存在很长时间了。为什么没人发现？

- 日常负载下，单个节点拉镜像回源也扛得住 — 只是稍微慢一点，容器还是能启动
- 没有报错，没有异常 — 因为代码走了正常的逻辑分支，只是"正常地做出了错误的决定"
- **没有「缓存命中率」和「续约成功率」的监控**，所以谁也没注意到 peer 节点其实一直在清空缓存

> 这种 bug 叫「潜伏型 bug」：它一直在，但在出事之前任何人都看不到它。等到故障发生、压力放大到足够大，它才暴露出来。
>
> 就像家里水龙头一直在滴水，但排水够快，你从没注意过。直到某一天你同时开了三个水龙头，水漫厨房，你才开始找问题 — 但其实水龙头一直都在滴水。

**【教训】** 没有监控的指标等于不存在。如果当时有「缓存命中率」和「回源比例」的监控，日常就能发现 peer 节点根本没在工作，不用等到故障来揭盖子。

### 2. 同一个 bug，不同压力下表现完全不同

| 场景 | 表现 | 结论 |
|------|------|------|
| 日常 1 个 Pod 重启 | 镜像拉取慢 2 秒，容器正常启动 | "没事，网络波动" |
| 5 个 Pod 同时重启 | 慢 10 秒，运维可能注意到了 | "仓库有点慢，再看看" |
| 3600 个容器迁移（这次事故） | 2000 个容器挂 1 小时打不开 | "事故！" |

**同一个 bug，只是因为压力大小不同，表现出来的症状从「完全无感」到「严重事故」跨越了好几个等级。**

这在分布式系统里非常常见 — 很多 bug 不是不存在，而是触发阈值太高，日常测不出来。等你出了事故复盘，回头看日志，发现异常信号早在几个月前就出现过，只是被当成噪声忽略了。

### 3. 越关键的东西，越难演练

事故反思的第 4 条是"每个季度做故障演练"。但这个建议有一个骨感的现实：

- 演练**应用层**（杀掉一个 Pod）→ 安全、好做
- 演练**基础设施层**（模拟交换机故障、压满仓库带宽）→ 如果环境不隔离，可能影响线上
- 环境隔离的代价很高 — 要另建一套镜像仓库、一套网络拓扑、一套完整集群

所以大多数故障演练只做**安全的那些**，真正有杀伤力的场景（大规模容器漂移、仓库被打满）反而没人敢做。**直到真正的故障替你做了。**

### 4. 告警不是给"错误"加的，是给"假设"加的

很多人认为：不出错的代码就不需要告警。

但这次事故里每一行代码都跑对了逻辑：
- 续约函数返回了 ✅（只是返回了错误的值）
- 缓存清空逻辑执行了 ✅（因为"没有存活容器"）
- 回源请求发出了 ✅（只是请求太多把仓库打慢了）
- 仓库在正常响应 ✅（只是慢了，没挂）

**没有任何一个环节抛异常，但从系统整体来看，结果是一团糟。**

所以正确的告警思路是：
1. 识别出系统里有哪些**隐式假设**
2. 给这些假设加上告警

| 隐式假设 | 应该加的告警 |
|----------|-------------|
| "peer 节点的续约一直能成功" | 续约成功率（< 99% 立刻排查） |
| "大部分请求由 peer 缓存服务" | 缓存命中率（< 50% 立刻排查） |
| "回源流量很少" | 回源比例（正常 < 10%，飙到 > 30% 告警） |
| "镜像仓库带宽够用" | 仓库出入带宽利用率（> 80% 告警） |

**能想到的假设都要加告警，而不是等代码报错。**

### 5. 「续约/保活」是所有分布式系统最脆弱的假设

续约机制的核心问题在于：

- **它假设「没收到心跳 = 死了」**，但「没收到心跳」也可能是网络延迟、时钟偏差、兼容性问题
- **它在自己最需要工作的时候最可能失效** — 故障时网络本身就不稳定，续约反而更容易超时
- **它没有降级路径** — 一旦续约失败，不是"慢一点"而是"完全不可用"

比如说，一种更鲁棒的设计是：**即使续约失败，不清空缓存，而是标记为「待验证」，继续提供 5 分钟的服务，同时后台重试续约**。这 5 分钟足够扛过突发流量高峰。退一步说，就算缓存已经是脏的，用旧版本镜像启动一个容器总比容器一直 Pending 要好。

> 续约是一个「要么全有要么全无」的设计，在某些场景下，应该改成「尽量服务，降级退让」。
