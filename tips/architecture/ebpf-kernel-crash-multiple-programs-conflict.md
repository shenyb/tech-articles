# eBPF 程序冲突导致内核崩溃：一个探针炸掉 900 个 Pod

## 先搞懂 eBPF 是什么（通俗版）

eBPF（extended Berkeley Packet Filter）是 Linux 内核里的一项技术，让你**在不改内核代码、不重启内核的情况下，在内核里跑一段小程序**。

类比成**给内核装传感器/探针**：

```
正常的内核：  ┌─────────────────────────────┐
             │  进程调度 / 网络 / 文件系统…  │
             └─────────────────────────────┘
             你只能从外面看，里面是个黑盒

装了 eBPF：  ┌─────────────────────────────┐
             │   [探针A] [探针B] [探针C]   │  ← 你在内核里插的监控程序
             │  进程调度 / 网络 / 文件系统…  │
             └─────────────────────────────┘
             你能实时看到里面发生了什么
```

eBPF 的常见用途：
- **观测/监控** — 看网络延迟、文件系统操作、系统调用耗时，不需要装 agent 轮询
- **安全检测** — 实时拦截可疑系统调用
- **网络加速** — 如 Cilium 用 eBPF 替代 iptables 做容器网络

**关键差别**：普通监控工具跑在用户态（挂了自己重启就行），eBPF 跑在内核态（崩了就是内核崩了）。

## 场景

2024 年，某团队在测试集群（其实跟线上共用一个内核）部署了 kindling 观测工具（基于 eBPF），想看看性能数据。但这个集群上已经跑着另一个安全部的 eBPF 探针。

灰度了 31 台机器，其中 24 台物理机陆续内核崩溃重启，900 个 Pod 被连带重启。

## 根因

**CentOS 4.18 内核的 eBPF 上下文清理 bug。** 流程如下：

```
时间线：
t1: eBPF 程序 A（安全探针）在内核中运行，处理某个事件
t2: eBPF 程序 B（kindling 探针）被加载，触发 hook
t3: 程序 B 执行完毕，按理说应该清理自己的上下文
     → 但 4.18 内核有 bug：B 的上下文没有被完全清理
t4: 程序 A 恢复执行
     → A 读到的是 B 留下的上下文（脏数据）
     → 执行现场错乱 → 内存访问越界 → 内核 panic → 整机重启
```

**两个关键条件缺一不可：**
1. 内核版本 4.18（旧内核，eBPF 的上下文隔离还不成熟）
2. 同时运行两个以上的 eBPF 程序

## 为什么说 eBPF 崩了比普通程序崩了严重得多

| | 普通程序 | eBPF 程序 |
|---|---|---|
| 运行位置 | 用户态 | **内核态** |
| 挂了影响 | 自己进程退出 | **内核 panic → 整机重启** |
| 连带影响 | 无 | 节点上所有容器全挂 |
| 调试难度 | strace/gdb 就能看 | 需要内核调试知识 |

这次事故里，**1 个 eBPF 探针的 bug = 24 台物理机重启 = 900 个 Pod 重建**。这还是在测试集群。

## 启示

### 1. eBPF 不是无风险的"观测神器"

很多人把 eBPF 当成"装上就完事的黑盒探针"，但忘了它本质上是在内核里跑代码。内核态的一个段错误不是 segfault，是 **kernel panic**。

警惕感应该类比成**给飞行中的飞机引擎装传感器** —— 当然可以装，但你得确保这个传感器不会掉进引擎里。

### 2. 多个 eBPF 工具的冲突问题会越来越突出

现在一个典型集群里可能同时跑着：

| 工具 | 用途 | 谁装的 |
|------|------|--------|
| Cilium | 容器网络（eBPF） | 云平台 |
| Falco / Tetragon | 安全检测（eBPF） | 安全部 |
| Kindling / Pixie / Bpftrace | 观测 profiling（eBPF） | SRE / 开发 |

**各自安装时都不知道对方存在。** 在内核层面，它们共享 eBPF 的 maps、hooks、程序链表，隔离性在旧内核上就是个问题。5.x+ 内核有 BPF_PROG_TYPE 和 BPF_TRACE 的完善隔离，但 4.18 这种老内核还在大量生产环境里服役。

### 3. 内核版本决定了 eBPF 的安全水位

| 内核版本 | eBPF 安全特征 | 风险 |
|----------|--------------|------|
| 4.x (早期) | 基本可用，缺边界检查 | Rust 之前的 C：自由但危险 |
| 5.x | BPF 验证器增强、BPF 链接 | 安全很多，仍有边界情况 |
| 6.x | 可休眠 BPF、原子操作、更严验证 | 接近生产安全 |

**如果你的生产环境还在用 CentOS 7（3.10 / 4.18），跑 eBPF 就要有"可能会崩"的心理准备。** 这次事故用的就是 4.18。

### 4. 重启修复的是状态，不是 bug

这起事故里，24 台机器陆续内核崩溃重启，但**重启后问题并没有消失**。因为这不是运行时状态污染（比如内存泄漏），而是内核 4.18 代码本身的缺陷。只要两个 eBPF 程序同时加载运行，上下文清理的逻辑就始终是错的，重启一万次也改变不了这个事实。

实际处理方式也说明了这一点：
- 不是"重启观察是否恢复"
- 而是**安全部直接停掉了其中一个 eBPF 探针**
- **直到某个探针被移除，崩溃才停止**

**判断一个 bug 重启能不能好，就看它的根因在哪层：**

| Bug 层次 | 根因 | 重启能好吗？ |
|----------|------|------------|
| 应用层（内存泄漏、死锁） | 运行时状态污染 | ✅ 能，但会复现 |
| 内核层（eBPF上下文清理bug） | 内核代码缺陷 | ❌ 不能，换内核或换配置才有效 |
| 硬件层（坏内存、坏磁盘） | 物理损坏 | ❌ 不能，换硬件才行 |

### 5. 观测工具本身也需要观测

这起事故的触发方式挺讽刺的 —— kindling 本身是**用来观测系统的工具**，结果它自己搞崩了系统。

> 在分布式系统里，观测链路本身也是系统的一部分。你的监控探针可能比你监控的服务更危险 —— 因为它有更大的权限、更低的可见性、更少的测试。

## 一句话总结

> eBPF 是内核的瑞士军刀，但刀在旧内核上可能会脱手。装之前确认三件事：内核版本够新吗？已经有什么 eBPF 程序在跑了？这个探针崩了我要怎么恢复？
