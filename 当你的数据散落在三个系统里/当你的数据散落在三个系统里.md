# 当你的数据散落在三个系统里

## 背景

几个月前，我们需要替换一个旧的坐席属性管理平台。

"坐席属性"听起来简单——就是一个坐席（客服人员）的分机号、直线号码、工号、办公方式这些信息。但问题在于：**这些数据分别属于三个不同的系统**：

- **HR/OA 系统**：存着员工的基础信息（姓名、部门、组织架构）和分机号
- **云电话系统**：管着员工的办公方式（在家办公/在公司办公）和销售侧手机号
- **直线号码系统**：管着直线号码和线路信息

也就是说，查询一个坐席的"完整属性"，需要串行调用三个独立的 RPC 服务，把结果拼起来。

## 原始方案：散落在各处

最直接的做法是——在业务代码里，需要什么数据就直接调哪个系统的接口：

```java
// 在某个 Controller 里
public SeatPropertyVO getSeatProperty(String userId) {
    SeatPropertyVO vo = new SeatPropertyVO();

    // 调 HR 系统
    UserInfo userInfo = userService.userInfo(userId);  // 可能失败
    vo.setUserName(userInfo.getUserName());

    // 调云电话系统
    String saleNum = phoneBarService.getHomeTypeMobile(userId);  // 可能失败
    vo.setSaleNum(saleNum);

    // 调直线系统
    DirectLine line = directLineService.directLine(userName);  // 可能失败
    vo.setDidNum(line.getLineNumber());

    return vo;
}
```

这个写法有几个问题：

1. **散落** —— 每个 Controller、每个 Service 里都可能出现这样的调用，没有统一入口
2. **没有容错** —— 任何一个 RPC 调用超时，整个请求就挂了
3. **没有重试** —— 网络抖动时直接失败
4. **没有监控** —— 不知道哪个系统经常出问题
5. **新人难上手** —— 新来的同事要搞清楚"这个字段从哪个系统来"，得翻半天代码

## 更糟的情况：你甚至不知道数据从哪里来

以上还是"你知道数据在哪"。更可怕的是——随着业务迭代和技术演进，一个项目的上下游系统可能会不断变化。比如：

- 分机号管理从 HR 系统迁移到了专门的号码管理系统
- 办公方式的数据源换了一个新服务

如果没有统一的数据聚合层，每次变更都要在**所有调用处**改代码。

## 解决方案：数据聚合层（Layer 模式）

我们做了一个很朴素的设计——**加一层**。

```java
// 统一的数据聚合层，每个 external system 一个 Service
service/layer/
├── UserOrgLayerService.java      // 对接 HR/OA 系统
├── PhoneBarLayerService.java     // 对接云电话系统
└── DirectLineLayerService.java   // 对接直线号码系统
```

每个 Layer Service 只干一件事：**封装对一个外部系统的所有调用**。

### 标准模式：每个 Layer 都长这样

```java
@Service
@Slf4j
public class UserOrgLayerService {

    @SCFClient(lookup = IUserService.URL)
    private IUserService userService;

    public UserInfo getUserInfo(String userId) {
        return getUserInfo(userId, 3);  // 默认重试 3 次
    }

    private UserInfo getUserInfo(String userId, int retry) {
        try {
            // 1. 调用外部系统
            CommonResult<UserInfoResponse> res = userService.userInfo(req);

            // 2. 处理正常返回
            if (res.isSuccess() && res.getData() != null) {
                UserInfo userInfo = new UserInfo();
                BeanUtils.copyProperties(res.getData(), userInfo);
                return userInfo;
            }
        } catch (Exception e) {
            log.error("getUserInfo err " + userId + ",retry " + retry, e);

            // 3. 重试耗尽后打监控 + 返回 null（不抛异常）
            if (retry <= 0) {
                WMonitor.sum("layer.user_info", 1);
                return null;
            }
            return getUserInfo(userId, --retry);
        }
        return null;
    }
}
```

三个 Layer 都遵循这个模式。区别只在于：调用的外部系统不同、返回的 DTO 不同。

### 这样设计的好处

**1. 调用者不用关心数据从哪里来**

业务代码只需要：

```java
UserInfo userInfo = userOrgLayerService.getUserInfo(userId);
```

至于这个数据是从 HR 系统、缓存、还是本地内存来的——调用者不关心。哪天换了数据源，改这一个文件就行。

**2. 容错统一处理**

所有 Layer 都有 3 次重试 + 监控打点。不会出现"这个接口忘了加重试"的情况。新加一个 Layer 时照着模板写就行，不会漏。

**3. 故障隔离**

某个外部系统挂了，不会拖垮整个服务。Layer 层重试 3 次后返回 null，上游业务可以选择用缓存数据、用默认值、或者报错但不要挂。

**4. 便于扩展**

后来我们需要加一个新的外部数据源（比如工号管理），只需要新建一个 `WorkNumLayerService` 就行了。既不影响现有逻辑，也不需要改动已有的 Controller。

## 流量路径

```
API 请求 → Controller → outter/Service（业务编排层）
                          │
                ┌─────────┼─────────┐
                ▼         ▼         ▼
           layer/     inner/     impl/
         (外部系统)   (业务逻辑)  (DB 查询)
                │         │         │
                ▼         ▼         ▼
           外部系统     本地逻辑    MySQL + Redis
           SCF 调用               (本地缓存)
```

- `controller/`：接收请求，参数校验
- `outter/`：业务编排，组装多个 Layer 的数据
- **`layer/`**：数据聚合，封装外部系统调用（核心）
- `inner/`：内部操作逻辑
- `impl/`：DAO 层，增删改查

## 踩过的坑

### 1. 重试次数统一但未必合理

所有 Layer 都默认重试 3 次。但有些场景（比如分机号分配）涉及分布式锁，重试时锁如果没释放好会出问题。更合理的做法是：**读操作可以大胆重试，写操作要谨慎**。

### 2. 外部系统挂了，业务方不知道

Layer 层重试失败后默默返回 null，调用方可能不知道数据缺失了。后来加了一个**兜底机制**：如果某个 Layer 连续失败超过阈值，发告警通知。同时从本地缓存（MemoryCache）中返回上一次成功的数据，不至于让前端拿到空值导致页面异常。

### 3. 缓存更新不及时

我们用了两层缓存：本地 MemoryCache（启动时全量加载）+ Redis。外部系统的数据变更通过消息总线（WMB）通知本服务，触发缓存刷新。但如果消息丢了，缓存就和实际数据不一致了。

解决方案：运维后台提供了手动刷缓存的接口，以及定时全量同步的兜底任务。

## 总结

"数据散落在多个系统"是企业级应用里很常见的问题——因为你不可能把所有人的数据都搬到一个库里。

Layer 模式的核心思路很简单：**不要在每个业务逻辑里重复写外部系统调用，统一收拢到一层，统一做容错、重试、监控**。

它不是什么精妙的架构设计，只是一个朴素的"加一层"思路。但正是这层，让后来的人改代码时少了很多"这个字段到底从哪来的"疑惑。

如果你也有类似的场景——数据散落在多个系统之间、每次查数据都要调好几个接口——可以考虑用 Layer 模式来处理。
