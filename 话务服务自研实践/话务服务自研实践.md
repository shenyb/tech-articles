# 呼叫中心话务服务自研实践：从FreeSWITCH ESL事件到业务落地的架构设计

## 1. 背景

公司之前使用的第三方呼叫中心系统到期，需要替换。话务服务作为呼叫中心的核心链路之一，负责将每通通话的全生命周期数据（振铃、接听、挂断、时长、录音等）采集、存储并推送到下游业务系统（客服、销售等模块）。

第三方系统在使用的几年中发现了一些痛点：挂机原因判断不准、事件处理不稳定、出现问题后修复手段有限。于是我们决定自研。

本文记录这个过程中的架构设计、关键实现以及踩过的坑。

## 2. 整体架构

话务服务采用**事件驱动模型**：

```
FreeSWITCH → ESL事件 → 消息总线 → EventDispatcher
  → EventProcessor（按事件类型分发处理）
  → MySQL（三张分表写入）
  → MessageAssembler（组装消息）
  → 消息总线（推送给下游业务系统）
```

- **技术栈**：Java 8 + Spring Boot 2 + MyBatis-Plus + MySQL + Redis
- **中间件**：消息总线（接收ESL事件+推送下游）、配置中心、分布式锁、监控系统

## 3. 核心设计：ESL事件处理管线

FreeSWITCH 产生的 ESL 事件通过消息总线到达服务端，经 `EventDispatcher` 按事件类型分发，`EventProcessor` 负责具体的事件处理逻辑。

### 3.1 事件类型

我们处理了 16+ 种 ESL 事件，覆盖一通通话的完整生命周期：

| 事件 | 处理内容 |
|------|---------|
| PRE_TRANSFER | 预转接绑定，建立原会话与目标会话的关系 |
| CHANNEL_CREATE | 呼叫通道创建，初始化话务数据 |
| CHANNEL_PROGRESS / CHANNEL_PROGRESS_MEDIA | A路/B路振铃开始 |
| CHANNEL_ANSWER | 接通，记录接听时间 |
| CHANNEL_BRIDGE | 桥接，坐席与客户建立通话 |
| CHANNEL_HOLD / CHANNEL_UNHOLD | 通话保持/恢复 |
| CHANNEL_MUTE / CHANNEL_UNMUTE | 静音/取消静音 |
| CHANNEL_ATT_XFER | 转接/咨询 |
| CHANNEL_HANGUP | 挂断 |
| CHANNEL_DESTROY | 通道销毁，最终状态判断 |
| CHANNEL_END (自定义) | 处理转热线/转IVR等特殊场景 |
| SESSION_END (自定义) | 会话结束后的数据兜底 |

### 3.2 并发控制

同一通话的多个 ESL 事件可能并发到达。我们使用分布式锁按 `callId` 加锁，确保同一通话的事件串行处理，避免数据竞争。

### 3.3 呼入/呼出/咨询/转接场景

通话场景非常多样：
- **呼入**：客户打进来，分配坐席
- **呼出**：坐席外呼客户
- **咨询**：坐席A咨询坐席B
- **转接**：坐席A转接给坐席B
- **机关枪呼叫**：一条线路占满后自动尝试下一条

不同场景下，A路（坐席侧）和B路（客户侧）的事件处理逻辑有差异，需要根据 `dialType` 和 `legName` 分别处理，并正确关联通话链路上的父子关系。

### 3.4 数据组装与分发

通话结束后，`MessageAssembler` 从三张表中读取完整的话务数据，组装成消息结构，通过消息总线推送给下游业务系统。

推送时支持区分：普通通话消息 / 双呼消息 / 转接咨询场景的溯源信息填充。

## 4. 数据存储设计

### 4.1 三表设计

为了分离业务关注点，我们将话务数据拆为三张表：

- **t_call_main（主表）**：通话基本信息，包括 callId、用户、线路、号码、业务属性、录音URL、挂机方向、失败原因等
- **t_call_timing（时间状态表）**：通话各环节时间点，包括请求时间、振铃时间、接通时间、结束时间、通话时长、振铃时长等
- **t_call_ext（扩展信息表）**：队列信息、IVR轨迹、满意度评价、静音时长、保持时长等扩展数据

### 4.2 分表策略

话务数据量大，按 `callId` 进行分表。通过自定义路由处理器切换到具体的物理表，同时支持按天分表来归档历史数据。

### 4.3 Redis 辅助

- 通话中的 callId 快速索引
- 通话并发量的分钟级监控计数
- 部分标记位缓存（如消息路由标记）

## 5. 数据处理与分发

通话走完完整生命周期后，服务端在一次事件处理中判断是否满足发送条件，将完整的消息推送给下游。

如果下游系统短暂不可用或推送失败，我们提供了：

- **按callId重新推送**：指定callId重新推送话务消息
- **按时间段批量重推**：指定起止时间和状态码，批量重新推送
- **重新转码**：重新触发录音转码流程
- **压测工具**：模拟批量数据推送用于验证下游稳定性

这些工具在日常运维中帮助很大，数据出问题时能第一时间修复。

## 6. 踩坑总结

### 6.1 挂机原因不准

这是呼叫中心行业的老大难问题。第三方系统在使用的几年中也一直不准。

我们做了三方面的优化，综合判断挂机原因，准确率超过了第三方系统：

- **FreeSWITCH 850 码分析**：FreeSWITCH 挂断时携带的 850 码（SIP挂断原因码）是最直接的信号，但单独使用可靠性不够
- **回铃音识别**：通过回铃音特征判断未接通原因（空号、关机、停机、占线等），覆盖了大量"无法接通"场景
- **A/B路 disposition 综合分析**：结合坐席侧（A路）和客户侧（B路）的挂断行为综合判断。例如：A路挂断且通话满足一定时长 → 坐席挂断；B路振铃未接通 → 客户未接等

### 6.2 ESL事件乱序

FreeSWITCH 的 ESL 事件到达顺序不一定可靠。在某些场景下，`CHANNEL_HANGUP` 事件可能先于 `CHANNEL_ANSWER` 到达，如果按到达顺序简单处理，会出现"还没接通就已经挂断"的矛盾数据。

我们做了大量兼容处理：

- **状态机容错**：事件处理逻辑不是严格线性状态机，而是幂等设计——重复或乱序的事件不会破坏已有数据
- **"先挂断后接通"的兜底**：如果收到 HANGUP 时还没有 ANSWER 记录，打上标记后交给后续事件或定时任务纠正
- **自定义事件补充**：新增了多个自定义 ESL 事件来补全通话生命周期——例如 `SESSION_END` 和 `CHANNEL_END` 在通话真正结束的节点发出，作为兜底信号，避免事件丢失导致的话务数据永久未完成

### 6.3 数据监控与快速修复

通话场景容错率低，数据丢了或错了直接影响到客服/销售的业绩考核。

- **多层监控告警**：关键指标（每分钟通话量、接通率、推送成功率、异常挂机率等）实时打点，超过阈值即告警
- **手工修复接口**：上述按callId重推、批量重推、重新转码等接口让运维人员可以在发现问题后直接操作，无需走发版流程
- **链路日志追踪**：每次事件处理都会记录操作日志，方便追溯"这条话务数据是怎么产生的"

## 8. 写在最后

从第三方系统切换到自研，过程并不轻松。但掌握了核心链路之后，我们发现能做的事情比以前多得多——问题自己能修、能力自己能加、数据自己能查。

最重要的是，这些沉淀下来的设计思路和踩坑经验，是花多少钱都买不到的。
